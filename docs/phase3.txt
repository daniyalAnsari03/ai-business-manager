=== WHAT TO BUILD ===

1. TRANSACTION LEDGER (new table, not just a balance number)

- Add a `wallet_transactions` table: id, business_id, type 
  (topup/spend/adjustment), amount, balance_after, gateway_reference 
  (nullable, the payment gateway's transaction id), status 
  (pending/completed/failed), created_at.
- Every change to marketing_wallet.balance must be accompanied by a 
  row here — the balance number alone is not sufficient audit trail. 
  This matches the spirit of AGENTS.md's emphasis on verified, 
  explainable results, not just a mutated number.
- RLS scoped by business ownership, same pattern as other tables.

2. TOP-UP FLOW (test mode)

- Build the actual top-up UI (extending the wallet screen shell from 
  earlier phases): quick-select amounts + a payment form using the 
  gateway's OWN hosted/embedded fields (Stripe Elements or equivalent) 
  — the app must NEVER see or handle the raw card number itself; only 
  the gateway's SDK should touch it. This is a hard requirement, not a 
  preference — confirm in your report that raw card data never passes 
  through your own server code.
- On successful test-mode payment: create a `completed` 
  wallet_transactions row (type=topup) and increase 
  marketing_wallet.balance by the same amount, atomically (both must 
  succeed or both must fail — no partial state).
- On failure: create a `failed` wallet_transactions row, show an 
  honest error message, and do not change the balance.

3. WALLET DASHBOARD — WIRE IT TO REAL DATA

- The existing wallet UI (available balance, monthly budget vs used, 
  daily spend list) must now read from real wallet_transactions rows, 
  not placeholder/zero values.
- Add a transaction history list (recent top-ups/spends) using the 
  ledger table.

4. TEST-SPEND TOOL (verification only, not a real feature)

- Build a simple, clearly-labeled "Simulate ad spend (test)" button, 
  visible only in a debug/test context (not the normal user-facing 
  UI), that deducts an amount from the wallet and creates a `spend` 
  ledger row — purely so you (and I) can verify the ledger and balance 
  math work correctly before real ad spend exists. Make it obvious in 
  the code and UI that this is temporary/test-only, and note in your 
  report exactly how to remove it later.
