# STEP 5 — GROQ FALLBACK CONDITIONS

Groq should be considered when Gemini cannot successfully complete the request.

Examples include:

* all usable Gemini projects are temporarily exhausted
* Gemini provider failures
* Gemini network failures
* Gemini timeouts
* Gemini provider errors classified as retryable
* all Gemini slots are cooling down and no Gemini slot can successfully serve the request

Do NOT treat every Gemini error as a reason to immediately use Groq.

Do NOT hide permanent programming errors by blindly falling back.

Classify errors correctly.

---

# STEP 6 — GROQ ERROR HANDLING

Groq errors must be classified separately.

Handle appropriately:

* HTTP 429 / rate limit
* authentication failure
* 4xx provider errors
* 5xx provider errors
* network failures
* timeout
* unavailable model

Do NOT treat a model-not-found error as a successful AI response.

Do NOT send the provider's raw internal error JSON to the user.

Return a safe user-facing error through the existing error handling system.

---

# STEP 7 — GROQ COOLDOWN

Implement a small temporary cooldown mechanism for Groq if the existing router architecture supports provider cooldowns.

Recommended behavior:

* 429 → temporary cooldown
* 5xx/network → short cooldown
* authentication/configuration error → longer cooldown or disabled state until configuration changes

Do NOT invent fake quota numbers.

Do NOT pretend to know the user's remaining Groq quota.

Do NOT repeatedly hammer Groq after a confirmed provider failure.
