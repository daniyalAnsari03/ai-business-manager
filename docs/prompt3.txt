==================================================
PHASE 3 OBJECTIVE
==================================================

Build the real Products and Inventory foundation of the AI Business Manager.

The business owner must now be able to manage real products through the application.

This is NOT just UI.

Products must be stored in Supabase PostgreSQL and must be isolated by authenticated business ownership.

The owner should be able to:

- view products
- add products
- edit products
- update stock
- view stock levels
- delete products where appropriate
- search/filter products
- see low-stock products
- upload a product image when practical

The implementation must work with the existing authentication and business setup from Phase 2.

==================================================
1. PRODUCT DATABASE
==================================================

Create the required Supabase migration(s).

Create a products table with a production-minded structure.

At minimum support:

- id
- business_id
- name
- description
- category
- price
- stock_quantity
- low_stock_threshold
- sku (optional)
- image_url (optional)
- created_at
- updated_at

Use appropriate PostgreSQL types and constraints.

Requirements:

- price must not be negative
- stock_quantity must not be negative
- low_stock_threshold must not be negative
- name must be required
- business_id must be required
- timestamps should be maintained automatically where appropriate

Create useful indexes for:

- business_id
- category
- name
- stock/low-stock queries where appropriate

Do not over-engineer the schema.

==================================================
2. BUSINESS OWNERSHIP
==================================================

Every product belongs to a business.

The authenticated user's business must be determined from the server-side session.

NEVER trust a client-provided business_id as an authorization mechanism.

The application must verify:

authenticated user
→ owned business
→ product belongs to that business

A user must never be able to read, create, update or delete another business's products.

Use Supabase RLS.

Create appropriate policies for:

- SELECT
- INSERT
- UPDATE
- DELETE

The DELETE policy is now allowed because product deletion is part of this phase.

Do not create broad policies such as:

"any authenticated user can access products."

Also ensure the required API role/table privileges exist, similar to the businesses table permissions fixed in Phase 2.

==================================================
3. PRODUCT SERVICE LAYER
==================================================

Do not scatter Supabase queries throughout UI components.

Create a focused product service layer.

The service layer should handle:

- getProducts
- getProduct
- createProduct
- updateProduct
- updateStock
- deleteProduct
- search/filter where appropriate

All operations must derive ownership from the authenticated server-side session.

Validate inputs before database operations.

Return predictable typed results.

Handle database errors safely.

Never expose raw database errors to normal users.

==================================================
4. PRODUCTS PAGE
==================================================

Replace the current "Products — Soon" placeholder with a real Products page.

Expected route:

/dashboard/products

The existing sidebar Products item should now navigate to this page.

The page must follow the existing premium design system from AGENTS.md.

Do NOT create a generic admin template.

The page should feel like part of the existing AI Business Manager.

==================================================
8. PRODUCT IMAGE
==================================================

Use Supabase Storage for product images if the existing Supabase setup supports it cleanly.

Create an appropriate storage strategy/bucket and policies.

Images must remain isolated by business ownership.

Do not expose private storage unnecessarily.

If a public bucket is the safest practical approach for product images, document the reasoning and ensure uploaded paths are business-scoped.

Support:

- image selection
- preview
- upload state
- upload failure handling

Do not make image upload prevent a product from being created if the image itself fails, unless the architecture requires it.

The product can exist without an image.

==================================================
9. EDIT PRODUCT
==================================================

Allow the owner to edit an existing product.

Editable fields should include:

- name
- description
- category
- price
- low-stock threshold
- SKU
- image

The owner must also be able to update stock.

Never allow negative stock.

Show a clear success confirmation after a successful update.

==================================================
10. INVENTORY / STOCK
==================================================

Stock is part of the Products foundation.

The owner must be able to see current stock.

Example:

Black Kurta
50 pcs

White Kurti
8 pcs

When stock is:

0
→ Out of stock

When stock is at or below low_stock_threshold
→ Low stock

Otherwise
→ In stock

The low-stock threshold must be configurable per product.

==================================================
11. STOCK UPDATE EXPERIENCE
==================================================

Create a simple stock update interaction.

Example:

50

New stock:

40

Save

Do NOT allow invalid negative values.

For now, stock updates are manual.

Do NOT implement automatic order-based stock deduction yet.

Order integration will be handled in the Orders phase.

==================================================
12. DELETE PRODUCT
==================================================

Allow product deletion with a confirmation step.

Example:

"Ye product delete karna hai?"

The user must explicitly confirm.

Do not immediately delete after a single accidental click.

Handle deletion failures safely.

If a product later becomes referenced by orders/sales, future phases may require soft deletion or restrictions.

For this phase, choose a production-safe approach that will not make future order relationships unnecessarily difficult.

If needed, use an active/archive mechanism rather than destructive deletion.

Document the choice briefly in the implementation report.
